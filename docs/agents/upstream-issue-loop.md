# 上游 bug：从症状到收口

**什么时候读**：发现 IB（手机端 / 电脑端）行为不对，或准备向上游提 issue / PR / 评论、收口一条已提的 issue 时。

**一句话**：**症状确定 ≠ 机制确定。** 先过三道闸门（能不能复现 / 谁的锅 / 机制清不清），再在出口处选一条路；**选路之前不要动笔写稿。**

---

## 一、三道闸门

### 闸门 1 · 能稳定复现吗

- **不能** → 走 `mobile-web-behavior-probe`：把症状收敛成**一个可改的变量**，做单文件真机对照页，一次只改一个变量。观测做成**勾选**（备注有歧义会把结论带反），测不到就写"未测到"，**别编**。
  - 产物 = **一条可稳定复现的操作序列**。这就是 `diagnosing-bugs` 那句"先造一条能变红的命令"在单文件应用里的等价物。
- **能** → 过。
- 环境提醒：**Service Worker 在 `file://` 下不注册**，本地测试必须起服务（`python -m http.server 8765`），页面带 `?v=N` 躲缓存。

### 闸门 2 · 是上游原版也有，还是只有我这里

- **只有我这里** → **不要去上游。** 先自查归属，镜像和纯拷贝要分开看：
  - **手机端镜像带自有补丁**（截至 2026-10-19：镜像 main＝上游 V3.1.1＋上下文账本模块，与上游不同源）⇒ `_check_sync.js` 那条"逐字节一致"**预期就会失败**，别再拿它当判据；改用**逐项比补丁台账**（`.scratch\ib-ctx-ledger\out\改动一览.md`，R1–R3＋patch12–33＋§二十四~§三十）。溯源到"上游原版有没有"要用 `_fetch_upstream.js` 取的原样快照，别拿镜像那份。r6/r7 时代的补丁重放工具链（`_patch_engine.js`／`_mk_summary_patch.js` 等）已于 2026-10-19 深清理移除——功能均已上游化，需要时从 git 历史取。
  - **电脑端**仍是纯拷贝，`node _win_check.js` 应报告零本地改动。
  - 再在 `file://` 与部署形态各测一次。
- **上游原版也有** → 过。
- ⚠️ 这是**判据**，不是感觉。把"自己改动引入的现象"报给上游，代价远超漏报（对方疲于解释，之后真问题也被淹没）。

### 闸门 3 · 机制清楚了吗

不清楚时两侧并行：

- **静态侧** —— `html-tool-offline-verify`（JS 语法 / 纯函数逻辑 / 渲染结构 / CSS 类覆盖）。3 MB 级单文件**别整个读**：`grep -n` 定位 + `sed -n 'A,Bp'` 读片段。
- **代码侧** —— **顺着调用点回查**。这是硬要求，不是讲究：2026-09-19 实测，两个子代理报的 5 条高危里 **2 条经回查不成立**、1 条把有意设计误报成缺陷。
- 不熟的仓库可以先 `research`，派后台 agent 出带引用的笔记。

#### 出口前的逐条清点

闸门 3 是要主动走进去的门，不是过路站 —— 从「能复现」直接跳到出口，往往就跳过了它。**选路之前**逐条确认：

- **每个下结论的代码点，是否读过它所在的完整判定函数？** 单看一行不够：`if(ts<=after)return` 看着像"到 after 就停"，但调用它的函数里可能还有另一个决定成败的判定。2026-10-10 实测：漏读 `_chapRangeM` 里的 `if(!(cut>after))`，把一次封章后的正常行为报成了"永久丢数据"，**该条被用户两次纠正后整条撤掉**。
- **这个行为是不是有意设计？** 提缺陷前先在说明书 / GUIDE 原文里找对应条目。2026-10-10 实测：「一次封一段、更早的由对话摘要兜住」已写在说明里，我读代码后没对说明书就报了缺陷。**判"是缺陷"之前，先找到说明书对应段落**，找不到再报。
- **归因类断言（"是因为 X 导致"）有两组独立数据吗？** 一组只能支撑"观察到"，支撑不了"因为"。2026-10-10 实测：一次实测得出"最早几天固化成锚点"，第二次实测直接推翻；**真正有说服力的是两次对照**（入参差 0～122 token 而输出差 2065）。只有一组就标"待验证"。
- **复现步骤里含"用户当时为什么这么做"时，动机来自用户，不是由现象反推。** 2026-10-10 实测：把切后台写成"因为没进度所以切"，实际是"以为后台会继续跑"—— 起因不同，正确的修法完全不同。**先问清起因再落笔。**
- **数字是从表格里读的？按列名取，不按列序。** 2026-10-10 实测：把「输入未缓存」与「缓存读」两列混淆、且把倒序列表当正序，写进了对外文稿的硬数据。见 `_check_tables.js`。

## 二、出口：五条路，选一条

**通道规则（2026-09-17 开发者原话，常驻）**：IB 的改动按"修订单 + 单文件提交"落进主线，**上游不合并任何 PR**；新发现**一律开 issue**，机制写在 issue 里。手上已经有实现时，在 issue 之外再挂一个"参考实现"PR 供对照 —— 见下表 ⑤。

> **原话存档（开发者对一份参考实现 PR 的完整回复，用户 2026-09-21 转述）** —— 这条完整展示了"逐条搬"的实际形态：
>
> > IB 的改动是按修订单一处处锚定落进单文件提交更新的，所以我决定不直接合并 PR，而是把方法逐条搬进主线：预遮罩竞态修正、进度条去掉 9 秒硬兜底改成看「预遮罩已撤 + 主界面已渲染」、openDB 的 onblocked / 超时 / onversionchange，这三处这一版就进；ib-sw.js 的超时与快速回退会进网页端。诊断面板和 VersionError 自愈暂不放——IB手机端 没有面向排查的界面层，网页端的缓存策略也比你手上那份简单。等真机复测确认白屏不再出现，#2 再关。
>
> 从这条能读出三件事，直接约束我们怎么切补丁、怎么写稿：
> 1. **粒度**：对方按"修订项"搬 ——「预遮罩竞态修正」是一处，「进度条去掉 9 秒硬兜底」是一处。补丁要照这个粒度切，切粗了搬不动、切细了对方拼不起来。
> 2. **不是全收也不是全拒**：同一条 PR 里三处这一版进、两处明确"暂不放"，理由是**对方的实现里没有那个前提**（手机端没有面向排查的界面层）。⇒ 提改动时要把**理由与前提**一起写清楚，对方才有依据挑；只写"这个更好"无法被采纳。
> 3. **收口挂在我们的验证上**：「等真机复测确认白屏不再出现，#2 再关」—— 关闭时机不由对方单方面定，而由我们的复测结果触发（与 §三 收口规则一致）。

| 路 | 做什么 | 代价 | 什么时候走 |
|---|---|---|---|
| **① 只报不改** | `to-spec` 出正文 → 过闸门 → 发 issue | 等对方把方法搬进主线 | 问题在启动层 / 核心链路，改它风险高。**实测有效**：PR #3 没被合并，但三处方法全进了主线，上游提交信息里还写了感谢 |
| **② 改在 fork 上提 PR**（旧形态） | fork 开一个分支改 → 按闸门 1 的环境自测 → 提 PR | 上游不合并，收益只剩"方法被搬走"；分支要能随时跟上游对齐 | 只在对方明确要一份 diff 时走；现行默认形态见 ⑤ |
| **③ 做成自用补丁** | 改 + 验证 → **先从镜像 Pages 撤下** → 进 `自用补丁-归档\`（手机端工作区） | 上游每次发版都要重放；而且**再也不能用"逐字节一致"来复核** | 上游明确不做、但确实需要 |
| **④ 先记着不处理** | 只落 `.scratch/<effort>/issues/NN-*.md`，不外发 | 无 | 属于那条很少用的线（如电脑端），或时机不对 |
| **⑤ 参考实现 PR**（现行默认） | 机制写在 issue 里；PR **只放可对照的 diff** → `--draft`、正文首行 `refs #N`、**不请求合并** | 多一道工序；分支要能随时跟上游对齐 | 手上已经有实现、希望对方"能对照"时。**收口**：对应 issue 关闭时一并关掉（见 §三） |

两条硬约束：

- **在镜像 `main` 上直接改 = 分叉。** 手机端镜像**已带自用补丁**（截至 2026-09-19：`fix-r6` 13 处锚点 ＋ 探针页，ahead 6 / behind 0）⇒ 它**不再与上游逐字节同源**，复核口径是**锚点等价核对**；要再往上叠改动，仍得先把改动挪出镜像、撤下线上。
- **电脑端已转入本地补丁模式**（`docs\adr\0003`，2026-09-21 起）：`桌面端目录` 不再是逐字节纯拷贝。核对判据＝**逐项比补丁台账**（`_patches\`（桌面端工作区），基线永不被写）；上游发版要**重打锚点**；上游若采纳某项要**撤掉对应补丁**。给上游提 issue/PR 时，行号仍以干净基线为准，正文「没动什么」要写明本地是补丁模式、PR 只含该修订项。

## 三、写稿与提交

### 动笔之前：先读实况

```bash
export GH_CONFIG_DIR="C:\Users\20513\AppData\Roaming\GitHub CLI"
gh api repos/<owner>/<repo>/issues/<n>            # 标题 / 状态 / 开立者 / 评论数
gh api repos/<owner>/<repo>/issues/<n>/comments   # 全部会话评论
gh api repos/<owner>/<repo>/pulls/<n>             # state / merged_at
```

**要读源码先取快照** —— 唯一入口，别裸 `curl`、别落工作区根目录：

```bash
node _fetch_upstream.js <commit> --expect-sha <sha256前缀>   # 落 Android\_up_<short7>.html
node _fetch_upstream.js --clean                             # 用完清掉（可重生成件）
```

派子代理时把**这条命令**写进它的 prompt。以前提示里写的是裸 `curl -o up.html`，结果子代理在工作区根目录留下一份 3.3 MB 的未声明残留；同一轮里同一份文件还被重复下载了 5 次以上。

两个坑：

- **PR 的会话评论要从 `issues/<n>/comments` 取** —— PR 在 issues API 里就是同号 issue；`/pulls/<n>/comments` 是**行内评审**，通常为空。
- **别信自己上一次的摘要。** 2026-09-19 实测：自家记录写着"上游没采纳我们的 accept 建议"，读实况才发现 V2.4.4 正是照那条建议改的，开发者的回复也早已写明"把方法逐条搬进主线"。

顺带核两件：`compare/<本地基线>...main` 看有没有新版本；`/commits/main` 看当前 head。

### 校正自家记录

读完实况**先回去改自己的文档**再动笔：每日日志、`MEMORY.md`、相关变更一览、归档 README。把「**我方主张未被采纳**」与「**上游自己就是这么设计的**」分开写 —— 前者不是缺陷，后者才可能是。

### 写"上游可发体"

六个段，一段不落：

1. **定位** —— 文件 + 行号 + 代码摘录，让人一眼能跳到那儿。
2. **机制** —— 为什么会这样；分支情况逐个列全（版本高/低、阻塞/拒绝……）。
3. **触发条件** —— 用户做什么会碰上；"单文件分发、多副本并存"这类常态前提要点明。
4. **现象** —— 用户实际看到什么。**环境写到浏览器一级**（"Android 端 Edge"），别只写"手机端"。
5. **诚实的验证状态** —— 没做真机复现就明写"目前完成的是静态与逻辑层验证，真机验证仍在进行中"。**不要**写"我这里没有浏览器环境"这类自述。
6. **没动什么** —— 明写"本地是上游的纯拷贝/同源镜像，未做任何修改；也未触碰远端"。

写作禁则见**用户级** `~\.workbuddy\MEMORY.md` 顶部的「对外文稿」一节（不用第一人称、不暴露版本迭代、不把我们的动作说成"顺手就做了"、称谓用「水老师」、不写像给对方派活的句子）。

### 过闸门

草稿**先给用户**，得到明确"发"才提交。落稿位置：`.scratch/<effort>/issues/NN-*.md`。

### 提交之后：回读核对

```bash
gh api repos/<owner>/<repo>/issues/<n>/comments
```

核对两件：内容与草稿一致；**「我」出现次数为 0**（"我们"也应为 0）。

### 收口

**收口 = 让一条已提条目走到终态**，要回答三件事：**回不回评论 → 谁点关闭 → 关联 PR 怎么办**。

三条路，**选完了要说出口** —— 只讲"收口"两个字，对方不知道指的是哪一条：

| 路 | 做什么 | 什么时候走 |
|---|---|---|
| **A · 回评论 ＋ 自行关闭** | 发一条确认评论，然后自己关掉 | 我们手上恰好有对方要的那个结果（复测通过 / 已在新版修好）。开立者关自己的 issue 是常规做法，也不给对方留待办 |
| **B · 只回评论、留给对方关** | 发确认评论，不关 | 对方明确说过"等某个验证之后再关"，让他自己收 |
| **C · 只关、不回** | 直接关掉 | 已经用别的方式闭环（如方法被搬进主线），再补一句只是噪音 |

⚠️ **关联 PR 与 issue 同进同退**：参考实现 PR（draft、正文 `refs #N`、不请求合并）在它对应的 issue 关闭时**一并关掉**；被否但方法已被搬进主线的旧 PR 也一并关掉，不留悬挂。
关闭前同样要**回读核对**：线上内容与草稿一致、「我」出现 0 次。

- **开立者本来就能关闭自己的 issue**，不需要写权限 —— 所以"要不要关"是选择，不是权限问题。
- **什么时候不该回**：对方说"等更多用户测试后再关"时，我们这一条确认帮不上忙，插一句只是噪音。判据是**对方在等什么**，不是手上有什么。
- **什么时候该回**：对方明说了"等某个验证结果"，而我们恰好有这个结果。

**不必走**：`wayfinder` / `to-tickets` / `implement-spec`（单个 bug 用不上）。
**看流程**：`retro` —— **单条 bug 的技术复盘不必走；一轮外发流程走完可以走**。复盘的是**agent 环境**（steering 文件 / 自动检查 / 工具），不是重评技术结论。2026-09-19 实测有效：一轮里跑出 8 条候选，其中"给「收口」下定义""建两个检查脚本"两项后来都真的落地了。
**看情况**：`grill-with-docs` —— 只在动机与边界还没想清楚时走；注意**它会写 `CONTEXT.md` 与 ADR**，在别人的仓库里跑要想清楚留不留（本空间已有 `CONTEXT.md`，在本空间跑没有这个问题）。

## 五、一条反直觉的判据

提新条目之前先问：**这一条能不能写成"另一端同一处已经有护栏、这一端还没有"？** 如果能，说服力远高于"这是新主张" —— 因为那批护栏是维护者已经认可并合入的东西，只需要问"要不要也搬过来"。2026-09-19 的电脑端两条就是这么定位的。
