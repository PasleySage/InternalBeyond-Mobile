# 写规格与拆票（本空间的三条实测经验）

来源：2026-09-19 那次完整外发流程（主动开口的「启动等待」：规格 → 7 张票 → 实现 → 两层 code-review → 真机 → 上线 → 上游 issue/PR）。

## Implementation Decisions 要逐处列改动

那次规格里"闸门位置"只写了一句笼统的话（"在心跳巡检的既有判断之前加一道判断"），而实现实际动了**两处** —— 心跳巡检，以及原生唤醒那条路径（不补的话，装了原生壳的场合会绕过闸门）。是 code-review 的 Spec 轴才发现"这处改动规格没点名"。

写规格时逐处列出：**改了哪几处、每处改什么、哪一处是例外**。"加在 X 之前，其余不动"这种写法，等于把"还有没有别的地方也该加"留给实现者去猜。

例外要写进同一段。那次是"等待期结束后的第一次机会不再掷随机概率" —— 不写清楚，审查时它就是擅自扩大的范围。

## 交付物相同的票，实现期边界会坍缩

那次拆了 7 张票，其中三张（等待期字段与界面 / 起点模式 / 导入保全）**实际是一次做完的**：它们的交付物是同一份单文件、同一个补丁集。按"每票一轮"开三张，等于多跑两轮没有内容的票面动作。

拆票时先问一句：**这几张票的交付物是不是同一个文件、同一个补丁集？** 是的话，在票里注明"可与 X 合并实现、合并验证"，省掉往返。

反方向仍然成立：**真能独立验证的票要分开** —— 那样每张票都能自己跑绿。

## 真机确认与上线必须分成两张票

真机确认只有用户能做，上线要碰远端。两者分开，且上线那张写明"**在确认通过前不得启动**"。

这条在 2026-09-19 的流程里起过作用：产物前后改了几轮（文案、档位、注释清理），而线上一直停在上一版已验证的文件上，直到用户点头才替换。
