### 乙-1 数据库版本高于页面时的报错文案指向错误的补救办法 · 中

- 位置：`index.html:4192`（`DB_VER=15`）、`openDB` 的 `req.onerror=()=>reject(req.error)`、`:12863` 的兜底文案
- 文案是「本地数据库无法打开。请换用 Chrome / Edge / Safari 直接打开本文件。」
- **问题**：真因通常是"本机库的版本比这个文件新"（先开过更新的版本，再回头看旧文件），换浏览器不解决任何问题——换成任何浏览器读的还是同一个高版本库。代码里也没有区分错误类型（`e.name === 'VersionError'` 本可分流），更没有"版本比页面新 → 清离线缓存 / 读旧版"的自愈路径。

- 备注：归档补丁里做过 `VersionError` 自愈（`ib_verfix`），上游未采纳。

- 位置：`ib-sw.js`（整文件仅 2,977 B）


- **问题**：没有完整性判断（响应是否读得完 / 体积是否对），入库前也没有剥 `content-encoding` / `content-length`。归档补丁里的完整性判断**未被采纳**。
- ⚠️ **提之前必须先自检前提**：现代浏览器的 `fetch()` 响应已由浏览器解压，且 `Content-Encoding` / `Content-Length` 属脚本不可见头（已被剥离），所以"入库不剥头 → 取出来被二次解压"这一条**很可能不成立**；而当时现场成立的是"拿解压后体积去比 `content-length` → 永不相等 → `index.html` 从未入缓存"（用户手机实测：缓存库里 2 条、没有 index.html）。**要向水老师提，先把这个前提核清楚，否则会递一个不成立的论据。**

### 乙-4 导航"快速回退"会让本次加载跑旧版 · 低-中（有意设计）

- 位置：`ib-sw.js`，`FAST_FALLBACK=3500`，有缓存时 `Promise.race([withTimeout(net,NAV_TIMEOUT), fast(3500ms→cached)])`
- **用户看到**：网络慢于 3.5s 时，本次显示的是**上一次缓存的整个应用**，后台再补写新缓存，下次打开才换新版。频繁发版的单文件应用里，用户可能短暂跑到旧版。

`maybeSummarizeM` 的失败出口共**五处**，全都返回同一个 `null`：`:9181`（**已有一轮摘要在跑**，`if(_summarizingM)return null` —— 同步返回，调用方**秒弹**）、`:9205`（窗口外消息 <2，**连请求都不发**）、`:9208`（没有可用 Key）、`:9218`（有响应但正文空）、`:9223`（请求期间封档线变了）。调用方 `:10906` 把这几类完全不同的失败写成同一句：`else toast('未生成：消息不足或 API 不可用')`（前面 `:10903` 已经弹过「正在整理中…」，所以并发早退时用户看到的是两句连续弹出）。

**2026-09-19 13:09 的新证据（补丁上线后的首次真机点击）**：用户点「立即更新」**秒弹**「未生成：消息不足或 API 不可用」。同一时刻台账上是**两次**调用 —— `入 1.1k / 出 655`（压缩旧摘要）与 `入 6.5k / 出 1.2k`（整合）—— 说明：

1. 这两次调用**不是**这次点击发出的（点击是秒返回的），而是**打开对话/发消息后自动触发的那一轮**（`:7273` / `:9474`）正在跑；点击撞上 `:9181` 被同步挡回 ⇒ 秒弹 + 旧文案。
2. 两次调用的输出是 **655 / 1200**，**不再顶到 4000** ⇒ 自用补丁 `fix-r6` 的 H2（下发 `thinking:{type:'disabled'}`）确实生效、思考不再吃满预算 —— 与本条结论互为印证。
3. 顺带暴露 `:9181` 这条早退**不设置任何真因**（`_sumLastErrM` 仍为空），所以即使打了 H3 的补丁，提示也只会回落到旧的通用句；且 H3 的 `_sumLastErrM` **从不被清空**，后续失败可能读到上一次的陈旧真因。**这两点已在自用补丁里处理并上线**：并发早退改提示「摘要正在整理中，稍等十几秒再点一次」，每次尝试先清空真因。**上游原版仍是这样，报 issue 时应把这条与 `:9205`/`:9208`/`:9218`/`:9223` 一起列。**

**机制**

1. 摘要走 `callAI` 的 OpenAI 兼容分支（`:8947-8957`），body 只有 `model / messages / max_tokens`。全文精确计数：`reasoning_effort` = 0、`enable_thinking` = 0、`"thinking"` 键 = 0；唯一下发思考参数的是 Anthropic 分支（`:8935` `b.thinking=_anthThinkShape(model)`），而且那是**开启**形态。⇒ 对 OpenAI 兼容端点（DeepSeek 官方预设 = `https://api.deepseek.com/v1/chat/completions`，`:4271`），IB **没有任何关闭思考的手段**：`thinkingEnabled:false`（`:9163`）只是不注入"必须写 `<thinking>`"的标签提示词（`:8871-8887`），管不到服务商侧的原生思考。
2. DeepSeek 官方文档（`api-docs.deepseek.com/zh-cn/quick_start/pricing`、`/guides/thinking_mode`）：`deepseek-flash` 与 `deepseek-v4-pro` **「支持非思考与思考模式（默认）」**、"思考模式默认打开，且 effort 默认为 `high`"；关闭需在请求里下发 `{"thinking":{"type":"disabled"}}`（OpenAI 格式）或 `{"reasoning":{"effort":"none"}}`（Anthropic 格式，"none 表示关闭思考模式"）。思维链经 `reasoning_content` 返回、与 `content` 同级 —— IB 的 `extractFull`（`:8563`）正是这么读的。
3. 于是：effort 默认 high 的思维链先花掉输出预算 → 预算耗尽时 `content` 为空、`finish_reason='length'`（`:9166` 那句"用思考文本当正文"的兜底**恰好**被这个 `finish_reason` 挡掉）→ `:9218` 返回 null → `:10906` 报"消息不足"。

**触发条件**：摘要专用API（或当前好友）指向一个**默认开启思考**的型号即成必然，与消息量、额度、网络无关。

**现象（Android 端 Edge / PWA，2026-09-19 09:40–11:26 用户实测）**：点「立即更新」→ toast「正在整理对话记录…」→ 约 20 秒后弹「未生成：消息不足或 API 不可用」；摘要"覆盖至"停在上一次成功的那天（本例 9/10）；同一对话正常聊天不受影响。

### 乙-9 「单次输出上限」在手机端对聊天与摘要都是空转（电脑端读它） · 中（2026-09-19 新增）

**位置**

- 手机端聊天主链：`genReply` 的 `:9287` 取 `pa=mpAi(cfg)`，`:9365` 交给 `callAIC(…, pa)`；而 `mpAi`（`:5381-5387`）的 base 写死 `maxTokens:4096`，per-AI 面板（`:11586-11598`）只写 `histLimit / grpLimit / postsLimit / ibfeedLimit / hbOff` —— **没有任何入口能写 `perAi.<id>.maxTokens`**（助手能看到的设置表 `PERAI_F`（`:24403`）里也没有这一项）。
- `_chatMaxTokensM`（`:8836-8843`）的判定顺序是 `pa.maxTokens > 0` **在前**、`_out.maxTokens`（＝「单次输出上限」）在后 ⇒ 聊天永远拿 4096，读不到用户设置。
- 摘要：`:9164` 直接传 `{maxTokens:4000}`，同样读不到该设置。
- 电脑端（对照，`:15055`）：

```js

```

⇒ **电脑端遵照用户的「单次输出上限」**，手机端不遵照。

**更硬的一条：手机端自己的界面文字承诺过"顶格给出"。** 同一设置的说明（`:3127`）：

> 一次回复最多生成多少 token（思考链与正文合计）。**此前固定为 4096，思考链稍长正文就会被截断成空回复；现与电脑端同口径顶格给出。** 个别中转不接受大上限时会按其报错自动降档，一般无需手动调…（`<!-- v130-p -->`）

也就是说 v130-p 的意图就是"手机端也读这个设置、按服务商顶格给"——但聊天主链经 `mpAi` 拿到写死的 4096，**这段意图在聊天主链上被绕过了**；摘要更是自己传 4000。⇒ 这不是"我们主张要可配置"，是**界面已经这么写了、代码没走到**。

**用户侧实测**（2026-09-19 12:02，用户把该设置改成 1024 之后）：新消息 `入 1451 / 出 1371` —— **出 1371 > 1024，设置未生效**；同一时刻 `_out.maxTokens` 确为 1024（助手走的 `out.maxTokens` 写路径 `:24413` 是有效路径）。

**顺带澄清一个容易误判的现象**：把该设置改成**档位之外**的值（如 1024 / 2048）后，界面上仍显示「自动」——这是**有意设计**，回填代码 `:11665` 的注释就写着"库值不在选项集时显示自动"，下拉本身也只有 7 个固定档（`:3126`：自动 / 4096 / 8192 / 16384 / 32768 / 65536 / 131072）。**界面看不到 ≠ 没写进去**；要读真值只能让助手报 `out.maxTokens`（设置表读的是库里的值）。⇒ 不要把它当缺陷报上去。（2026-09-19 用户实测矩阵，与这条规则逐格吻合：设 **8192 → 界面 8192**、设 **65536 → 界面 65536**；设 **1024 / 2048 → 界面「自动」**。同一时刻助手报出的库里真值就是用户设的那个数。）⇒ 手机端这个设置项在聊天上是**空转**。

**与乙-8 的关系**：同一块"输出预算"问题的两面 —— 乙-8 是摘要的 4000 天花板与误导文案；乙-9 是这个设置项管不到手机端的聊天与摘要。**因此按 `:9367` 那句提示去「调大单次输出上限」在本端是无效补救**（用户当时就是这么处理后认为"换了"，实际是那几轮思考没吃满而已）。

**外发口径（待定）**：可单独提，也可与乙-8 合并写成"输出预算相关的两处"。
