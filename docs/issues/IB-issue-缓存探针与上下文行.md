# 缓存探针加强与消息上下文行

**目标仓库**：`Sui-IB/InternalBeyond-Mobile`（issue）
**形态**：只报不改（机制写在正文）；参考实现见同目录 PR 稿
**基线**：上游 `040bf2a5` / 应用内 `v310-p`（2026-09-27）

---

## 现象

提示缓存偶发整段重建时，现有「缓存探针」只报断点字符位置与上一轮最新消息起点，不报：

1. 本轮真正发进 API 的历史条数（用户无法手数，也看不出是否跨过上下文窗口边界）
2. 断点两侧各是什么内容（只能推断是 system 块还是历史开头变了）

真机案例：连续多轮 ✅ 后单次 ❌，断在第 16692 字符，而上一轮最新消息起点在 2706052；用量从「缓存读 105856」掉到「缓存读 7040」。因缺少条数与片段，无法在当场区分「历史窗口滑动 / always 条目改动 / system 块改写」。

## 机制

`_ibOaiCacheDiagM` 在逐字比对时已经算出公共前缀长度 `d`，也持有两轮的完整序列化串，但落盘字段只有 `ok / d / total / last`。补两个字段即可定位：

- **条数**：本轮与上轮的 `msgs.length`。条数变化或跨过 `histLimit` 边界 → 窗口滑动；条数不变而前缀变 → system / 历史被改写。
- **断点片段**：`d` 前后各约 48 字的旧/新对照。一眼可见是哪一块在变。

消息详情面板（`openMsgInfo`）已有 Token 行，补一行「上下文：N 条进历史 / 上限 M · system K 字」即可，数据在 `genReply` 组包时随手可得（`hist.length` / `_histLim` / `sys.length`）。

## 建议修订项（供逐条搬）

1. **缓存探针记录条数**：诊断记录增加 `n`（本轮条数）与 `prevN`（上轮条数）。
2. **缓存探针记录断点片段**：出 ✗ 时截取断点两侧旧/新各约 48 字。
3. **缓存探针文案输出**：条数与片段随「缓存探针」本地指令一并展示。
4. **消息详情「上下文」行**：Token 行下显示进历史条数 / 上限 / system 字符数（`ctxStat` 随消息入库）。

前提：均为诊断展示，不改请求体、不改缓存策略、不改历史窗口算法；对无 `usage` 的老消息该行自动不显示。

## 环境

- 服务商 DeepSeek（官方 key），模型 deepseek-flash
- 上下文消息条数：全部（999）
- 对话摘要覆盖范围：上下文条数之外的旧消息

## 收口

真机再遇 ❌ 时，能用新字段当场区分窗口滑动与 system 改写，即算达成。
