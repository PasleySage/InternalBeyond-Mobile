# 主动开口加「启动等待」开关，而不做"同步感知"

**Status:** accepted（2026-09-19）

用户同时用手机端与电脑端，两端靠手工导出/导入备份互传。他遇到的现象是：**一打开手机端（浏览器标签页或桌面 PWA），半分钟到一分钟内 TA 就主动发来一条消息**——此时他还没导入，两端已经对不上。他明确不愿削弱主动开口这项能力，只想"别在我刚打开、还没同步的那一刻抢话"。

**决定：加一个用户可见的开关「打开应用后等待」**（等待时长 1/5/10/15/30/60 分钟可选、起点可选"仅冷启动"或"冷启动＋回到前台"、默认关），在心跳巡检的既有判断之前加一道闸门；到点后交回原有判据、不额外掷随机概率；被按住的"想说话"不排队补发；新增的三个字段在导入时做**本端保全**；电脑端本期不改。

之所以是"闸门"而不是"改判据"：TA 想说话，本来就意味着原有判据（距该对话最后一条消息已超过间隔）已经成立。因此只需在打开后按住一段时间，到点后原判据自然仍成立 —— 用户要的"等到 X 分钟后立刻发"不需要任何新逻辑。

## Considered Options

- **同步感知解锁**（打开后等用户完成导入/导出才解锁，5 分钟兜底）：最初的首选，被否。它要求定义"什么算一次同步"，且行为依赖"导入/导出"这个用户动作的时机，"它为什么现在说话了"变得无法一句话解释。
- **启动后固定静默 N 分钟（不可配）**：被否。用户要的是一个看得见、能自己调的开关；且"仅冷启动"与"含回到前台"应对的是两种不同的打开方式，不能替他二选一。
- **到点强制发一条（跳过原判据）**：被否。会出现"用户刚聊完它又自己发一条"；而且原判据本就会成立，强制发属于多余机制。
- **关掉「定时推送」**：被否。等于砍功能，与用户"不削弱"的取向直接冲突。
- **只治聊天里的主动开口、不治社交圈自动发布与对话摘要**：选用。后两者性质不同（一个是对外发布、一个是派生数据），用户选择本次不动。
- **导入时保全本端专有字段**：选用。否则一份不含新字段的旧备份会把用户刚设好的等待参数整条覆盖掉。

## Consequences

- 默认关 ⇒ 不开启时行为与现在**完全一致**，没有任何隐性改变。
- 开启后，每次"打开"（是否包含回到前台取决于所选起点模式）都会先安静一段时间；这是用户主动选择并可见的代价。
- **导入语义出现第一个例外**：导入「设置」模块时，本机偏好记录里的三个新字段会被取出并写回，不再是无条件"同 id 整条覆盖"。这条例外必须一直写在这里，否则将来核查"导入为什么没把某项换掉"会找不到解释。
- 新字段随「设置」模块**跨端流动**：电脑端本期不认识它们，但在读改写那条记录时天然保留（它是读改写，不是重建）。因此电脑端无需改动；若备份里根本没有这些字段，则要靠上一条的保全来兜。
- 自用补丁与上游的差距再拉大一档；上游发版后需重打这一处锚点（沿用既有锚点式流水线）。
- 等待期内不补发 ⇒ 不会出现"等待结束后一次收到多条"的行为。
