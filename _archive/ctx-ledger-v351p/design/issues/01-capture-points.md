## Question

| 路径 | 位置 | 注入点数量 | 备注 |
|---|---|---|---|
| 一对一主聊天 | `genReply` `:10655` 起 | `parts` 21 / `tails` 11 | 主战场 |
| 群聊 | `:12283` 起 | 8 个 push | 文案措辞不同（群成员 vs 单人 TA） |

| 自动续写指令（⚠️ 非共读学习室） | `_WS_CONT_PROMPT_M` `:10424`；`callAIC` `:10451` 使用 | — | 原误标为共读学习室提示；共读间实为 `quiet:true` 频道、走 `genReply`（见 Answer §0、§2） |

要定的：

1. **捕获函数长什么样** —— 一个 `_ctxSnapM(push)` 包装，还是在 `parts.filter(Boolean).join()` 与 `sys` 落定那一刻一次性取？后者更少侵入，但拿不到分组名（`parts` 是扁平数组，没有标签）。
2. **`hist[]` 怎么算** —— 它是 `buildHist` 的产物，不走 `parts`/`tails`。是单独一段（"历史与摘要"），还是逐条消息列？逐条在百条量级会毁掉可读性。
3. **群聊与主动开口这一轮做不做** —— 影响埋点数量与文案。
4. **`_SYS_SPLIT_M` 怎么归** —— system 被这个 `\u001e` 分成两块（块一=协议，块二=档案核心+人格收束，见 `:10757`）。账本要不要按这个天然分界切？它是缓存断点，按它切有额外好处。

## 已知约束

### 0. 结论速览

1. **用户可见的组包路径只有三条**：`genReply`（`:10655`）、`genReplyGroup`（`:12209`）、`_hbFireFor`（`:18531`，sys 部分走共享 builder `_hbCtxFor` `:18516`）。
2. **共读间不是第四条路径**——它开的是 `quiet:true` 频道（`:30313`），聊天照常走 `genReply`；共读常量块经 `ctx.sys.set` → `window._ibAppSysM`（`:6754`，在 `:10732` 被消费），书页 tail 经 `ctx.chat.send(text,{tail})` → `window._ibAppTailM`（`:16141`，在 `:10765` 被消费）。**观影室频道同构，一并自动覆盖。**
3. **捕获方式用混合制**（详见 §5）：语义源头处用「已有的命名变量」逐条记块；密集的能力协议区（15 个小 push）用**字符检查点差值**记为一块；**不**包装每一个 push、**不**在 join 后一次性取。
4. **`_SYS_SPLIT_M` 作为一等分界切开**（详见 §6）：账本两块与 anthropic 实际的两段缓存断点 1:1 对齐。
5. 埋点**分三层落地**（详见 §7）：规格写全三层，**参考实现 PR 覆盖全部三层**（2026-10-14 用户修订）——`genReply`（第一层）＋`genReplyGroup`（第二层群聊）＋`_hbCtxFor`/`_hbFireFor`（第三层主动开口）；二三层无真机验证，稿中标注「源码判断、未真机验证」。

### 5. 对「要定的」第 1 点：捕获函数长什么样

**推荐混合制，否决两个极端：**

- 否决「`_ctxSnapM(push)` 包装每个 push」：30+ 处 push 全部改形，侵入面最大，且包装层一旦写错就动了请求数组。
- 否决「join 落定后一次性取」：`parts` 是扁平数组、无标签，只能拿到总字符——等于回到旧稿的计数，答不上「哪一部分」。
- **混合制**：①语义源头处（内容已在命名变量里）调一次 `add(id, 变量)`，genReply 约 20 个块、多数与现有 push 语句同行；②协议区 15 个小 push 不逐个碰，用两处 join 长度检查点记一块 `dm.sys.protocols`；③tails 11 块在各自 push 处就近记。
- **关键架构**：捕获层只存稳定块 ID 与实测值；约 6 个语义组名是报告层的可改映射，不进捕获代码——真机分布出来后改组名不用重打埋点。

### 6. 对「要定的」第 2、4 点：hist 与 `_SYS_SPLIT_M`

- **hist 记为一整块、绝不逐条列**：块内附「N 条（user x / assistant y · 图片 z 帧）」与字符/估算值；摘要备忘存在时单列为 `dm.hist.summary`。百条量级逐条列出会毁掉报告可读性，且每消息预览对历史块无增量价值（预览机制留给语义组）。
- **按 `_SYS_SPLIT_M`（`\u001e`，定义于 `:15964`）切 system，强烈建议**：
  - 块一＝人设/用户资料/工具/能力协议；块二＝档案核心＋冷读＋前情提要＋人格收束（`:10757`）。
  - 它**正是 anthropic 的缓存断点**：`callAI :10242` 按此拆出 `_sysTail2`，`:10304` 据此下发两个带独立 `cache_control` 的 system 段。账本块与真实缓存段 1:1 对齐 ⇒ 「哪块花了多少」直接对应「哪段缓存有多大」，零成本的额外收益。
  - 报告中两块作为 system 的两个一级分区呈现；协议区是块一内的一个子块。

### 7. 对「要定的」第 3 点：群聊与主动开口这一轮做不做

**规格写全三层，实现分层落地（对齐 Code style「分层生长」与 #13 逐层采纳的成功先例）：**

- **第一层**：核心模块 ＋ `genReply` 埋点 ＋ 入库 ＋ 水水/面板两入口报告。一次覆盖**一对一、安静频道、共读间、观影室**——后三者零额外埋点（报告标签取 app hook 的 app 名；安静频道协议区天然为空）。
- **第二层**：`genReplyGroup` 埋点（§3，约 15 个记块点，每成员一份快照）。
- **第三层**：`_hbCtxFor`/`_hbFireFor` 埋点（§4，记块点很少，但要在两处主动消息 dbPut 前挂快照）。
- 外发 issue 把三层埋点表全部给出，**PR 覆盖全部三层**（2026-10-14 用户修订），两处入口（水水指令＋面板行）一并给；二三层无真机验证，稿中如实标注「源码判断、未真机验证」。

### 8. 失败时的降级行为（每处埋点统一规格）

> ⚠️ **2026-10-16 修订（用户提出；对参考实现 PR 是硬约束）**——「空」与「没采到」必须可区分：
>
> - **每处 `add()` 无条件执行**：不管功能开关开没开，都调一次；值为空串也记 `{id, 0}`，**不跳过**。
> - **报告层决定渲染**（三种态分开处理）：
>   - **正常空块**（如安静频道协议区天然为空）：不显示；
>   - **本应存在但为空的块**（如 `dm.sys.tools` 未配 MCP、`dm.sys2.amcore` 无 always 条目）：显式 0，让用户知道「开关开了但没生效」；
>   - **埋点异常块** `{id, missed:1}`：显示「本轮未计入」，让用户知道是工具问题。
> - **依据**：不同用户开了不同的能力开关 ⇒ 组包时某些 push 不执行；若「空就不显示」，用户无法区分「这块本来就空」和「埋点没采到」。与 mem 块已定的处理模式同源——「检索命中 0 条（当轮无注入，合法态）」（见票 09「外发前宜补」与两份稿 §9）。
>
> 原各条保留于下，与上文不冲突处继续有效。

- `add()` 内部 try/catch：失败只跳过该块；可在块表留 `{id, missed:1}`，报告显示「某块本轮未计入」，**绝不抛入 genReply/genReplyGroup**。
- `snapshot()` 失败返回 null：请求照发、无账本；`saveAi` 对缺账本字段按「无 usage 的老消息」同款处理（该行/该指令不显示）。
- 账本不触发自己的重试与独立落库：随消息 dbPut 的成败由现有保存流程兜底。
- 图片不数字符：历史块单列图片帧数，报告写「图片 N 帧不计字符」，避免假零。
