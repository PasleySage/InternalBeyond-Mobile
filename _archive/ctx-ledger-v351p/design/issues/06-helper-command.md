# 水水指令的形态与措辞

Type: prototype
Status: resolved（2026-10-14）
Blocked by: 04 ✅（2026-10-14 resolved）

## Question

水水抽屉里的本地指令已有三个（`缓存探针` / `图片探针` / `设置清单`，见 `:32154`）。新增的这条要答：

1. **指令词叫什么** —— 用户在聊天里问「有没有办法看上下文日志」，他在水水里敲什么？候选：`上下文` / `上下文账本` / `上下文（账本）` / `上下文透视`。**指令词要短、要像用户会说的话**（TA 说的是「看上下文日志」，不是「查 token 分块统计」）。现有三个的规律是双字或三字（`缓存探针` / `设置清单`）。
2. **报告长什么样** —— 已定用 Markdown 列表（`.hp-m` 是 88% 宽气泡）。⚠️ 走列表不是渲染器限制（旧版基线曾不渲染 table；当前基线 9ae7034a 已含 table 分支，2026-10-14 实跑验证），而是「与两个诊断探针调性一致、固定语义序更适合逐行、88% 气泡下列表更易读」。但具体措辞没定。参照现有两个探针的写法：
   - 缓存探针：每轮一行 `- ✓ 14:02 · 深水：system 与历史前缀稳定（16692 / 2706052 字符）`，**结尾一段解释**（「✓ 这轮能命中… ✗ system 或历史前缀变了…」）
   - 图片探针：同样每条一行 + 结尾解释
   账本要不要照抄这个「列表 + 结尾解释」的结构？解释那段写什么——是解释「怎么看这份账本」，还是给出「怎么省」的建议（后者 map 里标为待决）？
3. **显示几轮** —— 缓存探针取 `.slice(-6)`。账本也 6 轮？
4. **没记录时的空态** —— 两个现有探针都写了空态文案（「还没有记录。让 TA 查看一条带图的动态…」）。账本的空态是什么？（一轮都没跑过 vs 跑了但老消息没快照——这两种空态含义不同，文案也不同。）
5. **要不要收进能力注册表** —— `:32088` 那份「能力注册表」里列了三个本地指令（`④ 本地指令「缓存探针」「图片探针」「设置清单」`）。新增这条要不要一并登记，让水水自己知道它会这个？以及 `:32002` 的 `QUICK` 快捷指令行要不要加一颗？

## 为什么是 prototype

措辞与形态是「长什么样」的问题，不是「是什么」的问题。手上已有缓存探针与图片探针两个可对照的实物，但账本的报告形态还没有。**做一版粗糙的报告样例（用假数据），放进水水抽屉里看实际效果**，再据此定稿——比在纸上推敲快。

## 约束

- 不走 API、不花钱（水水本地直答，与缓存探针同规格）。
- 不新造界面：只加一条指令，复用 `addBubble` 与 `paintAll`。
- 措辞对标现有探针的调性：**陈述事实 + 解释含义**，不写「检测到异常」这类吓人的词（除非真的异常）。

## Answer（2026-10-14 定稿）

### Q1 指令词：`上下文账本`，认别名

- 注册名 / 显示名：**`上下文账本`**。
- 匹配式：**`/^上下文(账本|日志)?[？?]?$/`**——认「上下文」「上下文账本」「上下文日志」（带不带中文问号/英文问号均可）。
- 依据：核查基线三个探针的别名做法——缓存探针 `/^缓存(探针|诊断|命中)?[？?]?$/`（`:32155`，后缀组带可选 `?`，**裸词「缓存」也触发**）；图片探针 `/^图片(探针|诊断)[？?]?$/`（`:32154`，**不认裸词**）；设置清单 `/^设置(清单|列表|表)[？?]?$/`（`:32156`，不认裸词）。按「缓存探针认别名就照做」定本式。
- 不误伤：「上下文怎么调」「上下文太长」等真问题末尾不是 `账本/日志`、也不是裸词，不会被这条拦截。
- 无第三路径（无硬编码白名单）。

### Q2 报告形态：Markdown 列表 + 轮间 `---` + 轮头 `##` 标题（A+B 分层）

- 主体走 **Markdown 列表**，复用缓存探针/图片探针「列表 + 结尾解释」的结构。
- 走列表**不是渲染器限制**：旧版基线曾不渲染 table；当前基线 9ae7034a 已含 table 分支（`:6205-6224`、`:6255`，2026-10-14 实跑验证）。选列表是因为「与两个诊断探针调性一致、固定语义序更适合逐行、88% 窄气泡下列表更易读」。
- **视觉分层（用户反馈：6 轮堆在一起、轮间只有 1 个空行、轮头/列表/底注权重接近，扫描易串）**：
  - 轮头由粗体改 **`##` 标题**（渲染器里 `##`→h3，明显变大、加重）；
  - 轮间插 **`---` 水平线**（`<hr>`），把 6 轮切成 6 块；
  - 二者组合（A+B）：轮头大、轮间有横线，层级为「大标题（轮头）→ 列表（分块）→ 小注（为 0 的组）」。
- 已验证的另外两个变体：C（blockquote 包裹）**不可行**——该渲染器对 blockquote 只做行内渲染、不递归解析列表，分块 bullet 会被压成一串带「-」的纯文本；D（轮头 N/6 序号 + 空 2 行）序号可行但渲染器会把连续空行合并（`:6284`），间距不增加。
- 不采纳用户提的代码块包裹：丢粗体、等宽中文不好看、灰底原始感，与诊断调性不符。

### Q3 显示几轮：沿用票 05 的 6 轮

- 显示**最近 6 轮**（与缓存探针 `.slice(-6)` 一致，6 轮是票 05 已定的快照保留量）。

### Q4 空态：两种，措辞不同

- **A（一轮都没聊过）**：
  > 还没有账本。和任一位 TA 聊上一轮——发一条消息、等 TA 回，账本在每轮请求发出前自动记下。
- **B（有对话，但老消息在记账功能启用之前、没有快照）**：
  > 这些消息都在记账功能启用之前，没有账本。新发一条消息给 TA，之后每轮都会自动记下（账本只保留最近 6 轮）。

### Q5 登记：进能力注册表 ④ + QUICK 加 chip

- 能力注册表 ④（`:32088`）登记「上下文账本」，并补一句「问『上下文花在哪 / 哪部分吃 token』时提一句」。
- QUICK 快捷行（`:32002`）加一颗 chip（插在「图片探针」后）。

### token 显示口径（重点：真值/估算分层，跨面板关系见下）

- **轮头**：`13:30 · 深水 · 总 12.8k (缓存 0) · 最大：功能与规则`
  - `总 X` = **i+cr+cw 全量**（API 真值三项相加——**2026-10-17 B 裁**：甲裁「＝usage.i、与面板『入』同数」作废，真机复测缓存命中时面板行 2.5k vs 表格历史 128k 认知割裂，见修订块第 5 条；**2026-10-17 R3 排版重构**：删总字数、标签缩为「总」）；

- **分块行**：`- 功能与规则：11,025 / 9,920 (87%)`
  - `字` = 该块 chars（估算）；`tok` = `_blogTokenEstM` 估算；
  - **占比按字数算、不按 tok**——避免两个估算相乘。
- **为什么这样分层**：轮头「总」是 API 真值（三项相加）、与组行估算同量级；分块拿不到真值、只能估算。换模型/中转站会漂的是分块估算，总量真值不漂。

### 「怎么看」段：v2' 结构（两块、去重）

- 第一块「**组名含义（六组按固定语义排序，没写完的均以“等”指代）**」，六组各一行（见下方最终报告全文）。

### 「为 0 的组」措辞

- 由「（其余组为 0：…）」改为「**（为 0 的组：记忆与档案）**」——原句「其余组为 0」有「其余组加起来是 0」的歧义；「为 0 的组」作定语，冒号后明确是哪些组各自为 0。
