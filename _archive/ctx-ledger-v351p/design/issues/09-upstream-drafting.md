## Question

终点是「一份能外发的方案」。前面几张票把技术决策定完，这张票把它们变成稿子。要答的不是技术问题，而是**怎么写才可能被接受**：

1. **走 issue 还是先问** —— map 已定走 issue ＋ 参考实现 PR。但上游有一条明确先例：**issue #13（封一章四条）是"提供思路 ＋ 参考实现"的成功案例**，作者明说"写法与你的草案不完全一样，但方向一致"，四条全采纳。可复用的打法：机制 ＋ 行号 ＋ 可选改法，不请求合并，PR 里 `refs #N` 互链。
   **本需求能不能照这个打法走？** 还是它太"加功能"而非"修缺陷"，作者可能更倾向不做？（对照：作者侧取向里明确不做表情包 / 播放器 / 颜文字 / 水水 / 精细文件工具。）
2. **口径写多细** —— 上游作者风格是「修订单 ＋ 单文件快照」。一份"上下文账本"是**新功能**，不是缺陷修复。稿子要不要退一步写成「诊断信息缺失」的现象（用户被八万 token 惊到、无法定位）＋ 逐条可搬的修订项？
3. **参考实现 PR 写多大** —— 参考实现只给最小可跑版本（按 map 的「不投机性抽象」铁律：捕获 ＋ 估算 ＋ 一个入口），还是两处入口都给？只给水水指令、面板行留成"建议"？
4. **哪些内容不进稿** —— 真实分布数据（`03` 的产出）要不要贴？贴了显得有说服力，但那是**用户自己库里的内容统计**，含TA 名字。要脱敏到什么程度？
