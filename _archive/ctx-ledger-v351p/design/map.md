# 上下文账本：让手机端能回答「哪一部分花了哪些」

## Destination

**一份能外发给上游的方案（issue ＋ 参考实现 PR 稿），规格定稿到可以照着写代码的程度。**

具体说，走到这张地图的尽头意味着：

1. 手机端每次请求组包完成时，能落一份**分块账本快照**（哪几块、各多少字符、估算多少 token、每块开头一段）
2. 这份快照有**两个查看入口**：水水抽屉的本地指令（Markdown 列表）、长按消息面板（真表格）
3. 分组名有**真机数据支撑**，不是拍脑袋定的
4. 写成上游可发体六段，落`.scratch/ib-ctx-ledger/`，**等用户点头才发**

**终点不是「功能做完并上线」。** 走到规格定稿、能落笔写稿即可；实现与真机确认是下游另开的事。

**本 effort 的硬约束**：

1. **不新造视觉。** 诊断信息一律进已有容器（水水气泡 `.hp-m`、长按面板 `openMsgInfo` 的 `mi-grid`）。不新建页面、不造折叠交互。
   - **唯一例外**：`openMsgInfo` 面板内的**诊断行级展开**——该面板本身就是「详情视图」（用户主动打开＝主动探索），行级展开是「详情中的详情」，语义一致。**此例外不外延**至其它容器（水水气泡、聊天主界面等仍不造折叠）。
2. **不改请求体、不改组包算法、不改缓存策略。** 本功能是**旁挂观测**，与缓存探针同一性质。
3. **组包时顺手记，绝不重算。** 重算要走记忆检索（判官调 API、向量要嵌入），花钱且结果会漂移；记下来的才是「那一轮真的发了什么」。
4. **口径公开。** 估算不是真值，文案必须写明「约」。

**iOS 约束（2026-10-12 查实，作为约束看，不开票）**

起因：群里一位iOS 用户自述「记忆库量特别大而且还是天杀的 iospwa」，担心触碰 iOS 对 PWA 的限制。

⚠️ **先纠一个错**：我一度把同群里那句「但你是不是重置了」读成"iOS 每次更新都要重置"，并据此推断 SW 缓存版本号硬编码会导致用户长期拿旧版、重装丢数据。**这个推断是错的**——重读那段对话，「重置」是那位用户在**担心**另一位用户更新时会不会重置，不是现象证据。**IB 的更新机制是好的**（见下表）。那类推断在写进票之前必须先回读原文。

| iOS 限制 | 真相 | 对本 effort |
|---|---|---|
| 7 天不访问清数据 | 真（ITP，iOS 13.4 起） | ⭐ **加了主屏幕即豁免**（独立计数器），且 IB 启动时已调 `storage.persist()`（`:14413`）→ 无影响 |
| 存储配额比 Android 紧 | 老说法的 50 MB 已过时；iOS 17 起主屏应用与浏览器应用同为磁盘 ~60% | 存储占用 Data 页已可见（`:18304`「本站存储 X/配额 Y」） |
| 无 Background Sync / Fetch | 真，永远不会有 | IB 不依赖（不做离线队列） |
| 通知无回复按钮 | 真 | 影响有限（推送走应用内轮询，非后台同步） |
| 蓝牙 / NFC / USB | 真，全禁 | 无影响 |
| 无一键安装按钮 | 真，只能分享菜单「添加到主屏幕」 | 仅安装引导 |
| **更新静默 + 无「清除缓存」按钮** | 真，iOS 无更新徽章，唯一刷新手段是删网站数据/删图标 = 全清 | ⭐ **真实存在**，但与本 effort 无关（属IB 整体更新叙事） |

**IB 更新机制已查实是正常的**：SW 注册 `:14423`（仅 HTTPS/localhost）→ `install` 里 `skipWaiting()` → 策略**联网优先**（`fetch` 优先、失败才回退缓存，见 `ib-sw.js` 模板）→ `activate` 清理旧缓存；`IB_VER` **写进导出的备份档**，用户可自查；PWA 卡明写「离线单文件无自动更新通道」——上游作者早知并写明。

**结论**：iOS 对本 effort **无决策影响**。快照 6 轮 ≈ 14 KB，对自述「量大」的记忆库是零头——**那条担心属于记忆库体积本身，不属于快照**，不进本 effort。

## Out of scope

- **让用户能编辑上下文** —— Prompt Inspector 的核心卖点（可改后再发）。IB 的世界观里 TA 感知不到这些面板，给用户一个上帝视角会破坏设定；且与「只读诊断」的定位不符。已判出，不因方便捡回来。
- **真实 tokenizer** —— 浏览器端没有可靠的中文 tokenizer，要引外部库。`_blogTokenEstM` 对中文占比高的 IB 已足够准，且零依赖零体积。
- **按真值校准分块** —— 已驳回：把估算偏差按比例摊给每块，得到「加总对但每块都错」的账本，比纯估算更危险（它看起来可信）。
- **完整原文快照** —— 已驳回：144 万字符 / 6 轮，且复制一份完整上下文落盘（含系统指令全文），收益递减成本剧增。
- **给协议块做精确 token 计数** —— 已驳回：协议区静态常量 5,973 字＋动态块约 2,000–3,500 字，全开约 8,000–9,500 字，**测试账号倒推（含工具块）约占 system 84%**——它不是大头这个旧判断**已被推翻**（2026-10-12 续）；但「不值得精确测」的结论不变：它是固定套话、随开关整块增减，账本给它一个「约」数就够。⚠️ 旧数字「5,849／45%／<3%」全部作废（来历不可考）。且 `_blogTokenEstM` 对中文为主的 IB 足够准
- **iOS 专属的存储降级 / 开关** —— 已判出：iOS 对本 effort 无决策影响（加主屏即豁免 7 天规则、IB 已调 `storage.persist()`）。开一张答案为「不加」的票没有意义（且违反「不写兼容垫片」的代码铁律）。⚠️ 但那条担心**本身未被回答**，它属于记忆库体积那条线，不在此处。
